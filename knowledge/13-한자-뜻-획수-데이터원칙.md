# 한자 뜻·독음·획수 데이터 원칙

## 1. 법적 사용 가능성
최우선 근거는 대법원 인명용 한자 조회와 「가족관계의 등록 등에 관한 규칙」 제37조·별표1·별표2이다.

첨부된 공식 인명용 한자표는 독음별로 한문교육용 기초한자, 인명용 추가 한자, 허용자체를 구분한다. 표 마지막의 주의사항에 따라 지정된 발음을 기준으로 사용하고, 일부 두음 관련 예외와 허용자체 규칙을 따로 처리한다.

## 2. 뜻과 훈
법원 표는 '이름에 쓸 수 있는 글자와 독음'이 중심이며, 작명에 필요한 모든 훈·뜻을 제공하는 사전은 아니다. 따라서 뜻은 별도의 신뢰 가능한 사전 출처와 결합한다.

현재 저장 구조:
- `meaning-senses.csv`: 한자+독음별 전체 사전형 의미
- `selected_sense_ids`: 특정 이름에서 중심으로 선택한 의미
- `naming_intent`: 그 의미를 선택한 작명 의도
- `semantic_risk`: 다른 뜻과 의미 근거의 주의 수준
- `interpretation`: 선택 의미를 자연어로 풀어 쓴 편집 해석

선택한 뜻이 한자 자체의 다른 뜻을 삭제하거나 바꾸지는 않는다.

## 3. 획수
획수는 특히 주의한다.
- Unicode Unihan의 kTotalStrokes는 IRG 관례에 따른 정보성 필드다.
- 한국 성명학에서 쓰는 획수 기준과 항상 같다고 볼 수 없다.
- 필획/원획/강희자전식 등 다른 기준이 있으면 출처별 값을 모두 보존한다.

권장 구조:
```
strokes:
  - count: 10
    standard: "source-A"
    source: "..."
  - count: 11
    standard: "school-B"
    source: "..."
```

## 4. 변이자·허용자체
정자와 허용자체는 Unicode가 다른 문자일 수 있다. 화면상 비슷하다는 이유로 자동 통합하지 않는다. 법원의 별표2와 인명용 한자표의 허용자체를 별도 관계로 저장한다.

## 5. 현재 데이터 상태
`data/hanja/`에는 2024-07-16 대법원 조회 기반 제3자 미러와 독음별 검색 인덱스가 있다. 이는 후보 탐색용이며, 최종 적법성은 현재 공식 조회로 다시 확인한다.

## 6. 파생 데이터 재현성
정규화·다중 의미처럼 코드로 파생 가능한 데이터는 `data/meta/build-manifest.json`에 generator를 등록하고 `npm run check:derived`로 현재 산출물과 일치하는지 확인한다.
