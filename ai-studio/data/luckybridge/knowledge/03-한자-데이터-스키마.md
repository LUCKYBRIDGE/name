# 한자 데이터 레코드 스키마

현재 저장소는 한자의 법적 독음 후보·사전형 의미·작명에서 선택한 의미·획수·학파별 해석을 분리한다.

## 의미
사전형 의미 키는 `(hanja, legal_reading, sense_order)`다.

- `all_sense_ids`: 해당 한자+독음의 전체 의미
- `selected_sense_ids`: 특정 이름에서 중심으로 선택한 의미
- `selection_origin`: 부모·사용자 선언, 편집 제안, 역사 기록, unknown
- `naming_intent`: 선택 이유. 모르면 null
- `semantic_risk`: 의미 근거와 다른 뜻의 주의 수준
- `interpretation`: 선택 의미를 풀어 쓴 편집 문장

실제 선택 객체는 `data/hanja/semantics/name-meaning-selection.schema.json`의 JSON Schema draft 2020-12를 따른다. 설명 원칙은 `name-meaning-selection.policy.json`에 분리한다.

## 법적 상태
인명용 허용은 문자 하나의 영구 boolean이 아니라 글자+독음+허용자체+기준일의 관계다.

권장 필드:
- jurisdiction
- reading
- legal_category
- allowed
- valid_from
- verified_at
- source_id
- source_version

현재 후보 DB는 2024-07-16 제3자 미러이며 현행 공식 전체 diff가 완료되지 않았으므로 일괄 `allowed=true`로 승격하지 않는다.

## 획수
Unicode 기술 총획과 성명학 method별 원획/필획을 분리하고 `method_id` 또는 `stroke_standard`를 기록한다.

## 작성 규칙
- 미확인 값은 null/빈 배열
- 다른 독음의 뜻을 결합하지 않음
- 선택 의미가 전체 사전 뜻을 덮어쓰지 않음
- 성명학 오행을 글자의 절대속성으로 저장하지 않음
- 파생 파일은 build-manifest의 generator를 우선 사용
